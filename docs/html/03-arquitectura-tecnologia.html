Patrón: Next.js App Router con una mezcla deliberada de Server Components (páginas que requieren guard de sesión/permiso antes de renderizar, para que la restricción de acceso ocurra en servidor y no sea evitable) y Client Components (interactividad: formularios, gráficos, timelines animadas). Los Route Handlers exponen la lógica de negocio como REST interno, consumido tanto por Server como por Client Components.

4. Estructura de directorios

app/                       # Next.js App Router — 1 carpeta = 1 ruta
  auth/                    # register, login, forgot/reset-password
  onboarding/              # welcome, wizard, processing, proposal, simulating
  dashboard/               # Portal cliente
  backoffice/              # Panel del asesor
  admin/                   # Panel de administración/gerencia

  schema.sql               # Schema base

Principio de organización: cada dominio de negocio (scoring, riesgo, permisos, ingresos, documentos) vive en un único archivo de lib/ con responsabilidad clara, consumido tanto por Route Handlers como por componentes de UI que necesitan la misma lógica.

5. Modelo de autenticación y autorización

  1. Autenticación: Supabase Auth (JWT), con sesión persistida en cookie httpOnly.
  2. Roles fijos: cliente, asesor, gerencia, admin, más custom.
  3. Guards de página: cada ruta protegida valida sesión y permiso en un Server Component wrapper antes de renderizar — no depende de ocultar un enlace de menú.
  4. Permisos granulares: una vista de menú = un permiso independiente. 4 capas independientes impiden que admin sea restringible: (1) CHECK en base de datos, (2) resolución de permisos que nunca consulta overrides para admin, (3) tipo TypeScript que hace un override de admin error de compilación, (4) filtro defensivo en lectura. Permisos temporales evaluados en query-time, sin depender de cron.
  5. Datos sensibles: el RUT del cliente se almacena cifrado, nunca en texto plano; se enmascara en toda vista de UI.

8. Despliegue

  • Repositorio: GitHub, rama master como fuente de verdad.
  • CI/CD actual: integración GitHub↔Vercel — cada push a master dispara build y deploy automático. ● Sin pipeline de tests pre-deploy todavía
  • Entorno de datos: Supabase (Postgres gestionado). En desarrollo local se usa Supabase local vía Docker Compose, con el mismo schema y migraciones que producción.
